Status: **in progress**. S3 remains open.
The native framework supports a small public contract and an official status module.
The source profile sets `sv.status=enabled`: default-enabled and non-required.
This profile does not define the required production service catalog.
See [plugin design](plugins.md), [system coverage](plugin-api-map.md) and [native SDK](plugin-sdk.md).

## Current framework

The Windows x86 SDK uses a versioned C ABI with explicit record sizes and the `__cdecl` calling convention.
The host offers status snapshots, console logs, owned commands, tick/stop events and optional capability lookup.
The first game read capability copies bounded snapshots with opaque references and world-readiness checks.
The loader checks metadata, dependencies and exact DLL approval before activation.
The explicit user-requested `--allow-unapproved-native` flag skips content approval, defaults off and prints a warning.
It preserves compatibility checks. Native code still has full process access and can corrupt memory, block or crash.

Live management uses safe points and standard input commands.
Disable removes host-owned registrations. Disabled native DLLs stay loaded until shutdown.
Module ZIP installation, updates and rollback use the private host lock and preserve private settings and data.
The installer creates new profile entries as disabled and does not approve native content.
Entity lifecycle integration is committed as `3fbcbf3`, and the first read API implementation is committed as `92854b1`.
The read capability uses generation-safe entity references. Its [contract and evidence](plugin-game-api.md) describe the implemented limits.
The write capability has nineteen validated methods, and chat commands reach plugins with public, admin or local levels.
A private message uses a per-connection filter in the packet writer. The same document lists them.

## Remaining work and order

The user set this order: finish framework tests, implement the full mapped API, then add production gameplay and administration plugins.
No new production plugin work starts before the complete mapped API proof.
Most mapped hook operations and many mutations remain unimplemented.
The read slice and nineteen write methods exist. NPCs, aim queries, sounds, pushes on body parts, shop and settings operations, and the gameplay events remain future work.
The [legacy module catalog](legacy-modules.md) names them as N8 to N19.
Core bond capacity guards are in place before creation and physics mutators. Their tests do not cover every writer.
The status command proves the framework, not NPC, mission, weapon or external service support.

Two NPC behaviors, a custom mission, a weapon effect and an external snapshot consumer remain future examples after their API support exists.
Each example needs explicit original-client limits and a repeatable check.
Administration, permissions, bans, remote administration and optional log services remain future modules.
Existing administration stays available until replacements pass focused checks.

The required production module catalog remains undefined.
A10, D11 and D12 also lack definitions. Their identifiers do not establish requirements.
Lua and WASM hosts remain later work. The current native SDK does not imply support for those hosts.
