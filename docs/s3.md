# S3 evidence

Status: **in progress**. S3 remains open.
The native foundation proves a small public contract and an optional official status module.
It does not establish the full platform described in [plugin design](plugins.md) and [system coverage](plugin-api-map.md).

## Current native foundation

The Windows x86 SDK uses a versioned C ABI in `src/plugins/sv_plugin.h`.
Its public records use explicit sizes, and its calling convention is `__cdecl`.
The host offers status snapshots, log output, owned commands and tick/stop events.
The contract does not expose internal game record pointers.

The loader reads a selected profile, module metadata and dependencies before activation.
Profiles distinguish required, default-enabled and optional modules.
Missing or incompatible required modules prevent normal startup.
The first proof profile uses the optional `sv.status` DLL. This choice does not define the production service catalog.

Native content approval identifies DLL bytes with SHA-256.
The loader checks approval before it loads a DLL. Changed bytes require new approval.
The explicit `--allow-unapproved-native` option bypasses content approval and prints a warning.
The user requested this option. It does not bypass API compatibility checks or make native code safe.
Native code can corrupt memory, block or crash the server.

Live management uses safe points and standard input commands.
Disable removes host-owned registrations. Disabled DLLs can remain loaded until shutdown.
Installation and replacement can require a restart.
These rules do not promise recovery after arbitrary native corruption.

## Recorded automated proof

The first native test run passed all 23 checks in `tests/test_plugins.py`.
CTest recorded the `plugin-lifecycle` result on October 26, 2026.
The local evidence is `build/server/Testing/Temporary/LastTest.log`.
Build outputs and test logs remain ignored local files.

The checks cover these groups:

| Group | Observed coverage |
| --- | --- |
| Lifecycle | Enable/disable, required activation and dependency ordering |
| Failure | Missing modules, missing dependencies, dependency cycles and failed enable |
| Ownership | Conflicting commands, registration cleanup and callback failure |
| Required services | Required activation failure and required event failure |
| Execution | Floating-point state restoration, bounded input and live input before end-of-file |
| Native approval | Hash output, exact approval, rejection of changed content and explicit bypass |
| Compatibility | API mismatch rejection with the bypass enabled |
| Profile input | Rejection of a module identifier that escapes its directory |

Repeat the focused check after a normal build:

```powershell
ctest --test-dir build/server --output-on-failure
```

The normal server and launcher build passed during this foundation work.
The latest launcher interface and package changes still need their own observed checks.
This record makes no claim about visual quality, package acceptance, launcher Start/Stop or client gameplay.
The deferred original-client playtest remains open.

## Remaining S3 work

The [system coverage catalog](plugin-api-map.md) defines the intended API reach and the current documentation limits.
Game mutation APIs, generation-safe references and per-system events need their own implementation and focused proof.
The status command proves the loader. It does not prove NPC, mission, weapon or external service support.

Two NPC behaviors, a custom mission, an effect with an existing weapon representation and an external snapshot consumer remain future examples.
Each example needs explicit original-client limits and a repeatable check.
Administration commands, permissions, bans, remote administration and optional log services remain future official modules.
Existing administration behavior stays available until a replacement passes focused checks.

The required production module catalog remains undefined.
A10, D11 and D12 also lack definitions. Their identifiers do not establish requirements.
Plugin package updates, private-data preservation, rollback and clean shutdown still need final milestone evidence.
Lua, WASM and the external SDK remain later work in S4.
